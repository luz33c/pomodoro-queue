01 · 架构图

数据怎么在四个部分之间流动

  1. 1Postgres 通过逻辑复制把变更交给 Electric
  2. 2Electric 按 shape 输出 HTTP 日志，代理转发
  3. 3集合带 Bearer token 订阅 shape，数据进本地
  4. 4页面实时查询集合；写操作调用离线动作
  5. 5发件箱联网后调用 oRPC，断网时排队
  6. 6Drizzle 事务写库并返回 txid；变更再经 1→2→3 回到集合，确认后去掉乐观层
  7. 7集合数据经 Electrobun RPC 存进主进程的 SQLite 文件

web 宿主跑同一份 apps/app：链路 1–6 完全相同，只是集合放在内存里（以后可加 OPFS 持久化）。所以服务端和数据层可以先在 web 宿主上验证。

05 · 约定

packages/db 和同步的几条规矩

  • 同步表：uuid 主键（客户端生成）+ 归属列（如 owner_id），Electric 用它按用户过滤
  • 写接口：在同一个事务里返回 txid；按 id 幂等，没有真正写入时返回 txid: null
  • 字段名：客户端配 snakeCamelMapper()，和 Drizzle 的属性名一致；同步行 schema 放 packages/core，用类型检查和 Drizzle 对齐
  • 改表：加新 → 迁移 → 删旧。代理里的 shape 带版本，老客户端用旧版本；客户端换版本时 schemaVersion 加 1，本地缓存自动重拉
  • 纯本地数据：结构变了要写本地迁移（没有云端可以重拉）；和同步数据用不同的集合 id
