03 · 架构原理

读走 Electric，写走 oRPC，桌面再落一份 SQLite

  1. 1Postgres 把提交的变更通过逻辑复制交给 Electric
  2. 2代理带 ELECTRIC_SECRET 向 Electric 取 shape，只转发协议参数
  3. 3集合带 Bearer token 订阅 /shape：先拿快照，再长轮询收变更
  4. 4页面用 useLiveQuery 读集合；写操作直接改集合，先进乐观层
  5. 5cloud 模式下，集合的 onInsert / onUpdate / onDelete 调 oRPC
  6. 6Drizzle 事务写库，同一事务取 txid 返回；集合等到这个 txid 出现在 ③ 里，再去掉乐观层
  7. 7桌面：集合的读写经 preload 桥和 Electrobun RPC 进 Bun 主进程，写进 SQLite 文件

读：shape 怎样只给你自己的数据

// 集合发起，带 Authorization: Bearer <Clerk token>
GET /shape/todo/1?offset=-1
  authenticateClerkRequest()   // 没有 token → 401
  resolveShape("todo", "1")    // 名字或版本不认识 → 404
  proxyShape()
    只留 offset / handle / live / cursor 等协议参数
    加 table=todo  columns=…
       where=owner_id = $1  params[1]=userId
Electric
  第一次：返回快照
  之后：live=true 长轮询，每条变更带 txids

写：txid 握手为什么不闪

todoCollection.insert(row)     // 乐观层立刻显示
  onInsert → client.todo.create({ id, title })
    db.transaction(tx =>
      createTodo  ON CONFLICT (id) DO NOTHING
      txid = getCurrentTxid(tx)
    ) → { txid }
    // 同一个 id 重放 → { txid: null }，不用等
  等 shape 流里出现这个 txid
    → 换成服务器的行，去掉乐观层

桌面：数据怎么落到 SQLite

todoCollection             // webview（apps/app）
  createElectronSQLitePersistence({
    invoke: window.tsuDesktop.sqliteInvoke })
    webview-bridge.ts            // preload
      Electroview RPC 请求 sqlitePersistence
        Bun 主进程 sqlitePersistence.handle(call)
          BunSQLiteDriver → bun:sqlite
            userData/tsu-app.sqlite

webview 不碰文件系统，也不 import electrobun；只认 shared/host/desktop-bridge.ts 这一个入口。

两种数据模式

模式 谁用 集合 存在哪 要登录
cloud web Electric 集合 内存，刷新重拉 要
local 桌面（P2） 持久化本地集合 SQLite 不要
cloud 桌面开同步（P4） 持久化 Electric 集合 + 发件箱 SQLite + 云 要

页面只认集合，不认宿主；模式由 shared/host 决定。

几个关键取舍

  • Electric 只读，写全走 oRPC。权限和校验只在服务端写一次，Electric 不需要理解业务。
  • 客户端生成 uuid，写入按 id 幂等。离线时排队的写操作重放多少次都只写一行。
  • shape 由服务端定死，并且带版本。客户端改不了过滤条件；改表时老客户端继续用旧版本。
  • SQLite 放在桌面主进程。持久化代码只进桌面包，web 包不变大。

05 · 缺陷分析

还有哪些坑

级别 缺陷 影响 打算
高 桌面还不能登录 桌面拿不到 token，就没法云同步；P4 卡在这里 单独做桌面登录（系统浏览器登录后回跳），和 P2 并行
高 Electric 停了，复制槽会一直攒 WAL Postgres 磁盘持续增长，最坏会把库写满 设置 max_slot_wal_keep_size；Electric 健康检查接告警
高 测试不在仓库里 驱动契约测试和端到端脚本都在临时目录，以后改坏了没人发现 收尾时搬进仓库，接到 test 脚本
中 改动都没提交 P0、P1 和其他会话的改动混在同一个工作区 你确认后按阶段分开提交
中 web 不支持离线 集合在内存里，每次打开都重拉；断网时写入直接失败 本期接受；以后再评估 OPFS 持久化（要先控住包体积）
中 冲突规则是"后到的赢" 两端离线改同一条的同一个字段，后到服务器的覆盖先到的 todo 这类数据够用；需要时按 updated_at 比较或做字段级合并
中 自己移植的驱动，依赖还是 0.x TanStack DB 升级可能改 API，驱动要跟着上游改 锁版本；每次升级重跑契约测试
中 纯本地数据没有迁移函数 schemaVersion 对不上时，本地集合直接报错（云端集合是清空重拉） 改本地集合结构时手写迁移；云端集合只升版本
低 每个用户一份 shape Electric 的磁盘和内存随用户数增长 用户多了再评估共享 shape + 按需加载
低 改同步表的 DDL 会让客户端全量重拉 迁移后短时间流量高 同步表的迁移攒在一起发
低 Backend API 签发的 token 没有 azp 脚本和服务间调用不能直接用这种 token 真有需要时单独给服务间调用设计鉴权
低 还没实测的 Docker 全栈镜像、Coolify 部署、大数据量下的桌面 RPC、多窗口 各自上线前补测
低 P0 的测试 SQLite 还在 userData 不影响功能，但会让人困惑 P2 清单里一起删
