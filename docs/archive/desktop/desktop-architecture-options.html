桌面端：三条"本地包"路线并排比较

三条路线都满足同一组前提，差别只在产品区代码住在哪、怎么到达桌面包。本页负责并排比较；每条路线各有详细计划。阅读顺序建议：先看 01 的三张卡，再看 03、04 两张表，最后看 07 的决策点。

决策（2026-10-24） 已选方案 C → 最终计划 窗口 加载本地包 views://mainview 登录 留在 web；桌面端会话交接另行计划 产品区 两端共用 Electrobun 2.x 主进程 bun；视图 Vite 构建再 copy

01三条路线

方案 A · web 双构建

把 web 的 /app 打包进 views://

apps/web 多一种构建模式：TanStack Start 的 SPA 模式产出纯静态文件，桌面端整份 copy。产品区是 web 新增的 /app 路由段，守卫改客户端。 

apps/web/
├── vite.config.ts          # mode desktop：base "/"、SPA 模式
├── src/start.ts            # desktop 模式跳过 clerkMiddleware()
├── src/routes/{-$locale}/
│   └── app/                # 产品区，客户端守卫
├── dist/                   # web 自己的 SSR 产物
└── dist-desktop/client/    # 桌面用静态产物
apps/desktop/
├── electrobun.config.ts    # copy ../web/dist-desktop/client
└── src/bun/index.ts        # preload 把首屏改回 /app
复用方式
产物复用（整个 web）
路由
只能 browser history；刷新深层路由待验证
Clerk
绑定 @clerk/tanstack-react-start
首次出窗口 1–2 天风险：views:// 刷新行为长期：靠 lint 守住"不碰 Start"
详细计划：desktop-plan-a-web-dual-build.md
方案 B · 共享包

页面抽成 packages/app，桌面端自己的 SPA 引用它

共享包只放页面主体和查询，不依赖 Start、Clerk。web 留薄包装；apps/desktop 带一个 Vite SPA（hash 路由）引用共享包。oRPC 客户端由各端注入。 

packages/app/
├── src/api/client.ts       # configureAppApi / getAppOrpc
├── src/api/queries/*
└── src/ui/dashboard/*      # 页面主体
apps/web/src/
├── pages/dashboard/        # Container + 共享页面
└── router.tsx              # 注入同构客户端
apps/desktop/
├── src/bun/index.ts        # 主进程
└── src/view/               # Vite SPA · hash 路由
复用方式
代码复用（包）；两端各加一层路由包装
路由
桌面 hash history；web 不变
Clerk
包只用 @clerk/react hooks；provider 各端自选
首次出窗口 3–5 天风险：低，结构上不可能碰 Start长期：每页两层包装
详细计划：desktop-architecture-plan.md · 总览图 · 运行时详解
方案 C · 独立产品应用

产品区独立成 apps/app，web 托管、desktop 复制

产品区是一个纯 Vite + TanStack Router 应用，一份代码两种构建模式：web 模式由 web 启动器托管在 /web/app/，desktop 模式 copy 进 views://。web 只剩营销页和登录注册。 

apps/app/
├── vite.config.ts          # mode web：base /web/app/ + browser
│                           # mode desktop：base ./ + hash
├── src/routes/             # __root、(auth)/dashboard
└── src/shared/             # orpc、host、locale、styles
apps/web/
├── server.ts               # 托管 /web/app/*，回退 index.html
└── src/routes/…/(auth)/dashboard/   # 迁入 apps/app
apps/desktop/
├── electrobun.config.ts    # copy ../app/dist/desktop
└── src/bun/index.ts
复用方式
产物复用（同一应用、两种宿主）
路由
web browser / 桌面 hash，运行时切换
Clerk
应用自己用 @clerk/react
首次出窗口 3–5 天风险：低，结构上没有 Start体验：营销页 ↔ 产品区整页跳转
详细计划：desktop-plan-c-product-app.md

02一句话区分

A：web 既是网站也是桌面包

最少改动，最快出窗口；但桌面包带整个 web，产品区永远住在 Start 构建里，"不能用服务器"只能靠约定。

B：页面是包，两端各自包一层

共享粒度最细，web 几乎不变；每个产品页要在两端各写一层路由包装，多一个注入点。

C：产品区是第三个应用

一份代码一次构建两端同用，桌面端最薄；代价是网站与产品区分家，跨边界整页跳转。

05登录推迟，各留什么口子

A

产品区绑定 @clerk/tanstack-react-start，它的 provider 依赖 Start 上下文。桌面接登录时要在 desktop 模式下替换或绕过。口子最窄。

B

共享包只用 @clerk/react 的 hooks（Start 版 SDK 本身就是 re-export）。桌面端 provider 与会话交接全部收在 apps/desktop。

C

应用自己持有 @clerk/react provider。web 宿主同源 Cookie 直接可见；桌面宿主的交接只改一个 provider 和 apps/desktop。

三条共同：API 已支持追加授权方（CLERK_AUTHORIZED_PARTIES），到时加 views://mainview；后端 authenticateRequest 支持 acceptsToken，OAuth PKCE 可选。

06已排除的路线

路线 排除原因
远程壳（窗口直接加载已部署的 web） 与"窗口加载本地包"前提冲突
系统浏览器登录 + 一次性票据交接 属于登录计划，不是架构选择；三条路线都兼容
本地 UI + 隐藏 web 窗口代领 token 依赖隐藏窗口和给远程页面开 RPC，Electrobun 文档明确不建议
Electron + @clerk/electron 偏离 Electrobun；SDK 仍是 Beta

07决策点

  1. 1选 A / B / C全部
  2. 2共享包或产品应用的名字：app / product / consoleB · C
  3. 3应用名与 identifier（你持有的反向域名）全部
  4. 4根 pnpm run dev 是否带上 desktop全部
  5. 5根 check 首次要联网下载 Hutch：接受还是跳过全部
  6. 6web 宿主下产品区用 browser history（启动器回退）还是也用 hashC
  7. 7web 的 /dashboard 是否迁到 /app/*：A 必须迁；B 可不迁；C 迁出 webA · B · C

08共同的 Spike（代码可丢，只留决策）

  1. pnpm 11 + Node 24 + TS 7 下跑通 electrobun dev；devkit 的 tsconfig 是否兼容 TS 7

  3. views:// 下 pushState、hash、刷新、前进后退的行为。A 依赖 pushState 的结论，B、C 只需要 hash
