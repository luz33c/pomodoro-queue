方案 B · 共享包 + Electrobun 本地包：它在运行时是怎么跑的

总览页回答"改哪些文件"。这一页回答"同一份页面代码，为什么能同时在 SSR 的 web 和 views:// 里跑"：依赖方向、两端的调用路径、注入机制、hash 路由、语言覆盖、开发与打包循环，最后是对照仓库代码的核对结果。

03注入机制：模块级函数，不是 Context

packages/app/src/api/client.ts
  let appOrpc = null
  configureAppApi({ orpc })   // 应用启动时调一次
  getAppOrpc()                // 查询里取；没配置就抛明确错误

packages/app/src/api/queries/get-private-data.ts
  getPrivateDataQueryOptions() = getAppOrpc().private.data.queryOptions()
  useGetPrivateDataQuery()     = useQuery(上面的选项)

web      router.tsx 顶层            configureAppApi({ orpc })  同构客户端
desktop  view/shared/api/orpc.ts 末尾 configureAppApi({ orpc })  纯客户端

为什么这样设计

  • 存的是客户端实例，不是用户会话。web 的同构客户端在服务端每次调用都重新走 Clerk 的 auth()，请求之间不会串数据。
  • 写法沿用仓库已有的 setClerkAuthTokenGetter（packages/api/src/client/tanstack-start/clerk-auth.ts），也符合 zustand.md 里"不默认用 React Context"的约定。
  • 页面不再直接引用 @tsu-stack/api/client/tanstack-start/orpc：那个模块含 createIsomorphicFn、Clerk 的服务端 auth() 和 appRouter，离开 Start 编译器会把服务端代码带进浏览器包。
  • 以后接登录时，再加一个同样形态的 configureAppSession()。

04路由：views:// 下为什么必须用 hash

打包后窗口加载的是一个文件。pushState 会把地址改成一个不存在的文件路径，刷新就找不到；hash 路由永远停留在 index.html。

场景 地址 刷新后
打包后首屏 views://mainview/index.html 正常
pushState 路由 views://mainview/dashboard 找不到文件，Electrobun 没有文档化的回退
hash 路由（计划采用） views://mainview/index.html#/dashboard 文件永远是 index.html
开发时 http://localhost:5180/#/dashboard 正常；但源是 http://localhost，不是 views://

路由表用代码式（routes/tree.ts 只有 / 和 /dashboard），不引入 router 插件和生成文件。web 那边不受影响，仍是 Start 的文件路由。

05语言：不重新编译，运行时覆盖

packages/i18n 编译产物   策略 ["url", "baseLocale"]，两端共用同一份
  ├── web      URL 里的 /de 决定语言                 ← 不变
  └── desktop  URL 永远是 index.html → url 策略只能得到 baseLocale
               view/shared/i18n/locale.ts
                 overwriteGetLocale(() => 设置里的语言 ?? 系统语言)
               messages m.* 原样复用

为什么不给桌面端单独编译一套策略

  • Paraglide 的 Vite 插件把策略编译进 packages/i18n/src/paraglide，这个目录是共享的。两个应用用不同策略编译会互相覆盖，同时开 dev 时还会来回打架。
  • 现有的 LocaleProvider 本来就是用 overwriteGetLocale 在客户端覆盖的，桌面端只是换了"语言从哪来"。
  • 已核对：产物里导出 overwriteGetLocale 和 overwriteSetLocale。

06开发循环与打包流程

pnpm run dev:desktop

  1. predev：构建 @tsu-stack/i18n
  2. dev:view：Vite 在 :5180 起 view，带 HMR
  3. dev:shell：electrobun dev --watch 启动主进程（dev 渠道）
  4. 主进程 HEAD http://localhost:5180 成功 → 窗口打开 dev server
  5. 改共享包或 view → 热更新；改主进程 → 自动重启

注意 开发时页面的源是 http://localhost，和打包后的 views:// 不同。Origin 相关的行为（CORS、授权方）必须用打包产物验证。

pnpm run build:desktop

  1. build:view：vite build（base: "./"）→ apps/desktop/dist/view
  2. electrobun build --env=stable：打包 bun 主进程
  3. copy：dist/view → Resources/app/views/mainview
  4. 输出 build/ 与 artifacts/，只能构建当前平台
  5. 运行时：渠道 ≠ dev → 窗口加载 views://mainview/index.html#/

为什么不用 Electrobun 自带打包器 它跑不了 Tailwind v4、Paraglide 这些 Vite 插件，所以视图一律 Vite 构建再 copy，参考仓库也是这么做的。

07四个阶段分别交付什么

Phase 0 · Spike · 1–2 天

先把不确定的事变成决策

  • pnpm 11 + Node 24 + TS 7 下跑通 electrobun dev
  • Vite view + Tailwind v4 在系统 webview / CEF 下的渲染
  • hash 路由切换与刷新
  • 调 health.live，记录 Origin
你会看到：一份决策记录（renderer、API 通道、TS 版本、dev 脚本）。代码可以丢。
Phase 1 · 共享包 · 1–2 天

页面搬家，web 不变

  • 新建 packages/app
  • 客户端注入 + 两个查询
  • dashboard 主体搬进包，web 改成薄包装
你会看到：web 的 /dashboard、/de/dashboard 行为与样式完全一样，只是代码换了地方。
Phase 2 · 桌面 · 2–3 天

窗口里出现同一个页面

  • ENV_DESKTOP
  • view：路由、oRPC、语言、主题
  • 首页 API 状态；dashboard 登录占位
  • 主进程：URL 切换、外链
你会看到：dev:desktop 能热更新；build:stable 启动后首页 API 状态为 Live。
Phase 3 · 工程化 · 约 1 天

收尾

  • 根脚本、catalog
  • 忽略配置、fallow 入口
  • .agents/desktop.md、packages/app/AGENTS.md 等文档
你会看到：pnpm run check 通过（运行前先征得你同意）。

08对照仓库代码的核对结果

已确认存在，计划可直接用

  • @orpc/tanstack-query 1.15 导出 RouterUtils 类型（AppOrpc 用它）
  • @tanstack/react-router 1.170 导出 createHashHistory
  • Paraglide 产物导出 overwriteGetLocale / overwriteSetLocale
  • @tsu-stack/api/routers/types 已是为客户端包准备的纯类型入口（extension、native 在用）
  • packages/db/AGENTS.md 先例存在，packages/app/AGENTS.md 照它写
  • #/ui/* → .tsx 单独一条映射，和 packages/ui 的做法一致

只能靠 Spike 验证

  • Updater.localInfo.channel()：来自参考仓库，官方文档没写
  • 外链拦截用 navigationRules 还是导航事件 + Utils.openExternal
  • views:// 请求实际带的 Origin 头 → 决定 API 直连还是主进程代发
  • devkit 的 tsconfig 与 TS 7 是否兼容；不兼容就像 apps/native 一样钉 TS 6
  • dev:view 与 dev:shell 的启动先后

建议调整一处：desktop 拆成两个 tsconfig

建议

计划里 apps/desktop 只有一个 tsconfig.json 并继承 devkit 配置。但 src/bun 要 Bun 类型，src/view 要 vite/client 和 DOM 类型，混在一起容易互相污染；拆开后 devkit 与 TS 7 的兼容问题也只影响 src/bun 这一半。 

 apps/desktop/
-├── tsconfig.json              # 继承 base + devkit，覆盖整个包
+├── tsconfig.json              # 只做引用：references → src/bun、src/view
 └── src/
     ├── bun/
+    │   ├── tsconfig.json      # base + .hutch/devkit/tsconfig.json，types: bun
     │   └── index.ts
     └── view/
+        ├── tsconfig.json      # base，types: vite/client
         └── …

提醒：计划的决策 9 把 web 的 /dashboard 留在原地，没有迁到 /app/*。这和"产品区将来独立成应用"的方向不冲突——packages/app 里的页面到时可以原样搬过去。
