PLAN C / INDEPENDENT PRODUCT APP

一个产品应用，
部署位置可以自由选择。

可以放在 app.xx.com，也可以挂在 xx.com/app。
产品区自己拥有页面、路由与构建。浏览器加载静态站，桌面加载本地包；两端共用产品代码。

01

独立的是产品应用，Web 托管只是一个选项

浏览器里的产品界面不需要经过 TanStack Start 渲染。它仍然需要业务 API、Clerk，以及你决定保留在 Web 上的登录入口。

apps/app

Vite + React + TanStack Router
产品路由 · 页面 · AppShell · 查询 · 样式 · 宿主集成

↓ 同一份源码，分别构建 ↓

浏览器版

build:web

dist/web → 静态托管

可以由 Web Node、独立静态服务器或 CDN 提供。拥有自己的 browser history 路由。

桌面版

build:desktop

dist/desktop → Electrobun copy

views://mainview/index.html#/dashboard
本地 UI + hash history。桌面会话交接以后单独规划。

共享产品逻辑；资源路径、history、认证入口、外链及原生能力等宿主差异集中处理。两端并非字节完全相同的一份构建产物。

Build independence

能独立构建

产品应用有自己的入口和构建命令，不引用 apps/web/src。它仍属于 monorepo，可引用共享包。

Runtime independence

能独立托管

部署静态产物即可运行浏览器界面，无须产品专属的 Start / Node 渲染服务。业务数据仍从 API 获取。

Release independence

可独立发布

独立静态部署可分别发布、回滚。如果把产物装进同一个 Web 镜像，发布周期就会随镜像绑定。

这里比较的是浏览器可见地址。两种形式均可承载同一个产品 SPA。

回到产品原页面

恢复目标地址，产品读取会话，再携带 token 请求业务 API。

同根域子域，可以共享会话

Clerk 官方支持根域与子域间的生产会话共享。xx.com 与 app.xx.com 通常不需要 satellite 多域方案。

  • 实例与 DNS：同一个生产实例、匹配的 publishable key，完成根域配置。
  • 子域许可：启用 Allowed subdomains 时，加入 app.xx.com。
  • 登录回跳：解析 URL 后校验 origin 与路径边界，保留原页面。

三个设置各管一件事

  • Clerk 子域 allowlist：哪些子域可以访问 Clerk Frontend API。
  • 业务 API CORS：浏览器能否读取业务 API 的跨源响应。
  • authorizedParties：校验 session token 的授权方；不能用 CORS 成功替代鉴权。

起草时的仓库让 CORS 与 authorizedParties 共用一个列表；当时的子域提案要求补入实际产品 origin；/app 路径不是新 origin。

独立前端仍有服务依赖。产品 UI 可独立托管，但业务功能需要 API 与 Clerk；你把登录入口留在 Web，新登录流程仍依赖该入口可用。桌面的 views:// 不属于这些 HTTPS 子域，会话交接保持后续单独设计。

迁移时保留用户切换后的 Query 缓存清理。共享会话不会自动共享 React 状态、QueryClient、主题或语言；本地开发实例的行为也不能代替生产域名验证。

05

目录保持独立，产物在部署时组合

现有 C 文档中的 apps/web → @tsu-stack/app 依赖用于把静态产物装进 Web 镜像。采用独立托管时，这条打包依赖可以省去。

应用各自负责什么

apps/
├── web/        营销、登录注册 · Start
├── app/        产品应用 · Vite SPA
│   ├── src/
│   │   ├── routes/  产品路由
│   │   ├── pages/   业务页面
│   │   └── shared/  API、auth、host、样式
│   └── dist/
│       ├── web/     → 静态托管
│       └── desktop/ → 桌面复制
├── desktop/    主进程、窗口、原生能力
└── server/     oRPC、鉴权、业务数据
packages/       ui、i18n、core 等共享包

独立子域的配置示例

# 起草时的规划示例，不代表当前环境变量配置
VITE_WEB_URL=https://xx.com
VITE_APP_URL=https://app.xx.com
VITE_SERVER_URL=https://api.xx.com

# 浏览器构建
base: "/"
history: browser

# 桌面构建
base: "./"
history: hash

VITE_APP_URL 是 C 计划新增配置。切换到同域路径时改为 https://xx.com/app，并同步资源 base、Router basepath 和入口路由规则。

部署 URL 通常需要在构建前确定。Vite 的 base 与客户端 VITE_* 会在构建时写入产物。从 /app 改到子域根路径通常需要重新构建，单改容器运行环境变量不会重写已生成的 JS。

本页用根域网站示例。仓库本地默认的 /web、/server 不是固定架构。原草案的 Web Node 托管规则实际挂在 /web/app；若保留网站 /web 却要产品使用顶层 /app，还需调整入口挂载或反向代理。

06

我的建议：C 保持独立，入口按发布需求选择

如果你准备让产品独立发布，我倾向 app.xx.com

网站、产品、桌面各有明确边界，产品使用根路径。起草时产品区只有一个较小的 dashboard，尚未形成大量路径兼容负担。采用独立静态托管后，产品更新无需重新发布营销站。

优先独立产品入口

选 app.xx.com。增加子域和静态部署目标，配置好 Clerk、API 来源与回跳。

优先少一个部署目标

选随 Web 镜像的 xx.com/app。保留独立源码和构建，接受与 Web 一起发布。

如果你既想要 xx.com/app，又想独立发布，选方式 ②。无需为了“独立”强制改变域名，也无需先把产品做成共享页面包。

01
先做本地包技术验证

确认 Vite 资源、样式、hash 刷新与实际 Origin；不提前实现完整桌面登录。

02
拆产品应用，完成浏览器链路

迁 dashboard，跑通选定部署位置、深链刷新、Web 登录往返和账户缓存清理。

03
桌面复制产品产物，分别发布

产品 Web 构建、Web 网站构建与桌面打包各自可执行；Web 部署无需下载桌面工具链。独立发布时保持 API 对已发布客户端的兼容。

这张图修订了原草案的哪些假设？
  • Web Node 托管是可选部署形态，独立产品应用不依赖它才能运行。
  • 同域路径也能独立托管；子域与独立服务器并非一一对应。
  • 两端共享产品代码，宿主差异超过 base / history；桌面登录不预设只改一个 provider 就够。
  • 登录回跳需完整处理 URL 与来源边界，不能仅放行字符串前缀。
  • 浏览器子域共享会话有官方支持，桌面自定义协议行为仍待实际验证。
  • 起草时仅更新本 HTML 的架构说明；该版本现已归档，当前 Markdown 与确认稿图解已另行维护。
