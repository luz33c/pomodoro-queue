## 目录与命名规则

1. **一需求一目录**：采用 `NNN-英文kebab名`（如 `001-pomodoro-queue`），编号递增、不复用；一个编号对应同一主线或同一批交付的需求。
2. **PRD 与 `system-design/`**：
   - 需求目录根下放产品需求与交互方案 HTML（`*.html`）。中小型需求允许把交互演示与简要改动合在同一份 HTML 中。
   - `system-design/` 放为实现该需求做的独立技术方案 HTML；只在技术复杂度高到需要独立成文时创建，无设计稿时不建空目录。
   - 长期跨需求的技术约定（同步、桌面、认证、工具链等）不放这里，统一维护在 `.agents/*.md`。
3. **文件命名**：
   - 带日期的演进稿/过程稿日期放前面：`YYYY-MM-DD-<主题>.html`，方便在文件树按时间排序。
   - 未拍板的多方案/多模型对比稿加 `draft-` 前缀：`draft-YYYY-MM-DD-<标签>.html`。
   - 拍板定稿后，定稿使用明确语义名（如 `prd.html`、`prd-desktop.html`、`prd-mobile.html`）；被淘汰的对比稿可直接删除（git 历史可找回）或靠 `draft-` 前缀与定稿区分。

## 生命周期（快照原则）

- 状态流转：`草稿` → `评审中` → `已定稿` → `开发中` → `已上线`
- **上线即冻结**：需求上线后，在总表标为 `已上线（以代码为准）`，不再为了后续小改动反向修改交互式 HTML。代码与 `.agents/*.md` 才是长期唯一的现行真相。

## 大需求 vs 小需求

满足以下**任意一条**即视为大需求，开编号目录；都不满足则按小需求处理：

- 用户可感知的新能力（新页面、新流程、新模式）
- 需要在多套方案之间评审选型
- 涉及数据库表结构或 API 变更，或跨两端以上（web / desktop / mobile）
- 一次提交做不完

### 小需求处理方式

- **不进 `requirements/`**：不单开目录，也不反修已上线需求的 HTML；需求和改动理由直接写在提交说明里。
- **需要看交互效果时**：让 AI 生成临时 HTML 到 `docs/scratch/`（`.gitignore` 已忽略），确认完即可丢弃，不提交进仓库。
- **改了长期技术约定**：同步更新对应的 `.agents/*.md`。
- **做着做着变大了**：发现需要比方案或改表结构时，停下来开新编号目录。
