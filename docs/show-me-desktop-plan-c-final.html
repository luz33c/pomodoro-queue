01 · 应用边界

apps/web

网站与登录入口

TanStack Start；负责公开页面、SSR、登录注册和校验后的 App 回跳。

apps/app

产品界面

Vite + React + TanStack Router SPA；包含 Dashboard、认证门禁与 AppShell。浏览器和桌面共用源码。

apps/desktop

原生窗口与打包

Electrobun 2.x 薄壳；Bun 主进程负责窗口、加载地址和外链。通过 copy 加载 App 产物。

apps/server + packages/api

业务 API

Hono + oRPC；由服务端验证身份。App 在两个宿主下都直接请求 API。

apps/app/src
  ├─ vite build ───────────────→ dist/web ─────────→ 浏览器
  │                                                ↑
  │                                  App 静态服务 或 Web 静态挂载
  └─ vite build --mode desktop → dist/desktop
                                  └─ Electrobun copy → views/mainview → 桌面窗口

浏览器 / 桌面窗口 ── oRPC（有 token 时带 Bearer）──→ API

App 页面不导入 Electrobun，也不导入其他应用源码。宿主差异集中在 src/shared/host/；AuthGate 是选择未登录界面的例外。 共享 UI、字体、主题与文案来自 packages/*。

02 · 两个宿主的实际差异

构建时通过 Vite mode 选择宿主
维度 浏览器 桌面
产物 dist/web dist/desktop
地址与路由 Browser history；basepath 来自 VITE_APP_URL Hash history；相对资源路径；打包入口 views://mainview/index.html
开发服务 默认 localhost:3002/app；同源挂载时由 Web 转发到 :3002 Desktop mode 的 localhost:3003；dev 渠道探测失败时回退到打包页面
未登录 跳到 Web 登录，并携带原页面地址 显示登录占位与公开 API 状态；当前无法进入受保护产品页面
外链 新标签页，带 noopener noreferrer 由壳拦截并交给系统浏览器；不依赖 target="_blank"
语言 App 路由无语言前缀；启动时按 localStorage → navigator.languages → 默认语言选择；切换语言后刷新

views:// 没有深层路径的 HTML 回退，所以桌面使用 hash 路由。 Web 与 App 的 next-themes 使用相同默认存储 key，同源挂载时共享主题存储，不同 origin 时隔离。 Web 语言由 URL 决定，App 语言按上表选择，两者不会自动同步；桌面存储也受 WebView 隔离影响。

03 · 浏览器登录已接线，桌面登录尚未接入

浏览器代码已接入

网站负责登录，产品 App 消费会话

  1. AuthGate 等待 Clerk 就绪；未登录时跳转 Web 登录页。
  2. Web 校验回跳 URL：origin 必须等于 App 来源，路径必须在 App basepath 内，按路径段判断。
  3. 登录成功后回到原 App 页面；App 每次 API 请求通过 getToken() 获取 Bearer token。
  4. 退出后返回网站；用户身份改变时，现有桥接组件调用 queryClient.clear()。

真实生产域名下的会话共享，仍需要匹配的 Clerk 配置和运行验证。

桌面认证占位

窗口已能运行，尚无桌面会话

  • useDesktopAuth() 固定返回已加载、未登录和空 token。
  • 桌面不挂载、不初始化 ClerkProvider；这不等于已验证 Clerk 代码全部从产物移除。
  • 占位页调用公开的 health.live，并提供打开网站的链接。
  • 浏览器登录后的会话交接、桌面 token 存储与刷新仍未实现。

API 自动允许 Web 与 App 的来源；桌面打包和开发来源通过 CLERK_AUTHORIZED_PARTIES 配置为 views://mainview 与 http://localhost:3003。目前没有主进程代发 API 的桥接层。

04 · 浏览器版有两种已实现的服务入口

示例地址用来说明配置；实际部署尚未选定正式生产域名。

独立 App 服务

Web → https://example.com
App → https://app.example.com
  • apps/app/server.ts 提供静态文件、SPA 页面回退和 /_health；有 basepath 时健康路由也在其下。
  • 缺失的带扩展名资源返回 404；带 hash 的构建资源使用长缓存。
  • apps/app/Dockerfile 与两份 Compose 配置均已有 App 服务。

挂在 Web 的同源路径

Web → https://example.com
App → https://example.com/app
  • VITE_APP_URL 与 Web 同源，且 App 路径位于 Web basepath 下。
  • Web 的 Dockerfile 按配置构建 App；apps/web/server.ts 在 Start 前服务 App 产物。
  • 开发时 Web Vite 已转发 App 路径到 :3002，包括首页后直接带 ?query 的请求。
  • Compose 的独立 App 服务不会自动消失；使用 Web 挂载时按部署方式选择服务。

一份 dist/web 对应一个地址。VITE_APP_URL、VITE_SERVER_URL、 VITE_WEB_URL、VITE_CLERK_PUBLISHABLE_KEY 在构建时进入前端；更换地址后需要重新构建。 桌面发布也必须使用生产值。

外置网关也可将 App 路径转发到独立 App 服务，但仓库未提供网关配置。 同源镜像构建仍按原始 URL 字符串前缀判断，尚未统一为运行时的 URL 规范化判定；请保持地址写法一致。

05 · 当前开发与构建命令

命令（仓库根目录） 实际行为
pnpm run dev 确保 i18n 产物，然后启动 i18n watch、server、web、app；不启动 desktop、extension 或 native。
pnpm run dev:desktop 先构建 App 桌面产物，再并行启动 :3003 与 electrobun dev --watch。API 服务需另外运行。
pnpm --filter @tsu-stack/app run build 构建浏览器版到 apps/app/dist/web。
pnpm run build:desktop 构建 i18n、App 桌面版，再由 Electrobun 构建当前平台的 stable 包；不代表产物已签名或可正式发布。
pnpm --filter @tsu-stack/desktop run build:canary 构建当前平台的 canary 包，用于检查真实 views:// 环境行为。

开发服务器加载成功时，Vite 为 App 界面提供热更新；--watch 负责主进程变动后的重新构建与启动。 dev 页面来源是 HTTP，不能替代打包产物的 views:// 来源验证。
