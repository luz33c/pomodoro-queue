# show-me 设计文档

产出一份能直接拿去评审的 HTML 页面。页面上半部分让人**看到并操作**做完以后的产品，下半部分讲**怎么实现、为什么这样设计**。评审的人应该先通过操作演示认可交互，再往下读实现。

两份范例，写之前至少打开一份对照：

- `docs/architecture/show-me-browser-task-open-space-2026-11-02.html`：单个可交互的演示，用开关切换布局和异常场景，下方有调用链路、按文件的 diff、边界情况表、待实机确认项。
- `docs/23/browser-takeover-design.html`：分步骤的产品画面，配泳道架构图、状态图、"后台只做几件事"的规则表，以及折叠起来的源码依据。

## 流程

### 1. 定范围（不改代码）

用一句话复述需求：用户在哪个界面、做什么、看到什么结果。再判断要动哪几层：AGUI 前端、daemon（`apps/server`）、contracts、浏览器。浏览器源码只读，凡是需要浏览器改动的，在页面上写明"交给浏览器团队"。

### 2. 调研：结论必须有出处

- 找到真实的组件、CSS module、数据来源（HTTP 路由、contracts schema、query key）和已有的原生能力（`apps/agui/src/lib/native-bridge/types.ts`、`bridge.ts`）。
- 浏览器能力以远端为准：在 `/Users/luz/code/ego-build/src/ego` 先跑 `git fetch origin main`，再用 `git grep … origin/main` 和 `git show origin/main:<path>` 查。重点看 `renderer/ego_object/ego_controller.cc`（侧边栏的 `ego.controller.*`）、`services/node/ego_bindings.cc`（CLI 的 `ego.*`）和 `docs/api/`。不要假设接口存在。
- macOS 上没有 `timeout` 命令，别用它包住 grep，否则会静默拿不到任何结果。
- 每条关键结论都记下出处（文件路径、commit 或 PR 号），写进页面。
- 产品的视觉数值从源码里取，见 [references/product-fidelity.md](references/product-fidelity.md)。

### 3. 定方案

- 先给最小改动集，保持现有行为；可选项单独列出来，不混进主方案。
- 被否决的路线用一句话说明原因，例如"为什么不走 daemon"。
- 方案要在当前浏览器版本下成立。依赖未合入的浏览器能力时，明确写出依赖。

### 4. 调用 show-me 并写页面

用 Skill 工具调用 `show-me`（args 写主题），按它的原则只放能说明问题的视图；页面结构用本 skill 下面的约定。从 [references/page-skeleton.html](references/page-skeleton.html) 起步。

- 路径：`docs/architecture/show-me-<主题>-YYYY-MM-DD.html`，主题用英文 kebab-case，日期取当天。
- 单文件，不引外部脚本、字体或图片；图标用内联 SVG。

### 5. 自检

- 在 Browser pane 打开文件，把视口调到 1280 宽，每个开关和场景都点一遍。用 `javascript_tool` 触发点击并读出日志行，再截图确认画面。
- 再看窄屏（< 820px），确认布局堆叠、没有横向滚动。
- 测完把视口调回 `desktop`，然后用 `open <路径>` 在默认浏览器里打开。

### 6. 汇报

结论先行（能不能做、改哪几层、要不要动浏览器），附页面链接，列出待验证项，然后问用户是否按方案实现。没有明确的实现指令就不改代码；如果要实现，先按 `AGENTS.md` 写 ExecPlan。

## 页面结构

各节按顺序编号，标题写结论，不写"概述"。

| 节 | 内容 | 必需 |
| --- | --- | --- |
| 头部 | 小字 kicker：`模块 · 功能 · 方案（未实现）`；h1 写用户能得到什么；lede 用两三句话交代结论和改动范围（哪些层要改、哪些不用动） | 是 |
| 01 交互演示 / 产品效果 | 真实产品画面，可操作。下方一行日志显示底层调用和返回值，例如 `ego.controller.openSpace(7) → true` | 是 |
| 02 调用链路 / 架构 | 只涉及一条调用路径时用 `<pre>` 调用树；跨进程或跨仓库时用 SVG 泳道图，步骤编号，配色说明放在图例里。加一个 callout 解释为什么不选另一条路 | 是 |
| 03 改动 | 按文件列 diff，代码风格与仓库一致（AGUI 用 tab 缩进），注释密度与周围代码相同；测试只列用例名 | 是 |
| 04 边界情况 | 两列表格：场景、行为。覆盖失败或资源不存在、非 Ego 环境、多窗口或多任务、键盘、进行中状态 | 是 |
| 05 实现前要验证 | 每项用卡片写清风险和怎么验证；可选项用一个 amber callout 单列 | 有未确认事项时 |
| 规则表 / 状态图 | 后台按状态做决定时，用"看到什么 → 做什么"的表加状态图 | 有状态机时 |
| 源码依据 | 用 `<details>` 收起，分"已有、直接用 / 浏览器要加 / 本仓库要加"三组 | 跨仓库时 |
| 页脚 | 写"设计整理，非实现完成声明"；如果有 ExecPlan，附上链接 | 是 |

## 交互演示怎么做

演示是整份文档最重要的部分，它要回答"做完以后长什么样、点了会怎样"。

- **画面还原产品**：用 Ego Lite 窗口模型，左边是 mainland（Spaces 总览或某个 Space 的页面），右边是侧边栏（对话记录、任务条或药丸菜单、输入框）。颜色、圆角、阴影、字号用产品 token，文案用产品里的原文（英文 UI 文案保持英文）。用户给了截图的话，画面要和截图对得上。如果截图是旧版，在 01 节说明 main 上的现状，必要时提供"截图版 / main 版"切换。
- **真的能点**：页面上有多个状态时，用一个状态对象 `S` 配合 `render()`，所有点击都走 `data-*` 属性和事件委托。不要只放静态截图。
- **场景开关**：在演示上方放分段按钮，覆盖布局变体、正常、失败、非 Ego 环境等场景；可选设计用复选框，方便对比；再放一个"重置"按钮。
- **日志行**：每次操作后显示调用了什么、返回了什么、界面接着做了什么，把交互和第 02 节的调用链路对应起来。
- **键盘**：如果真实产品有键盘行为（菜单里的方向键、Esc、焦点归还），演示里也要模拟，并在说明里写出按键顺序。
- **动效**：只用短暂的进入和高亮（≤ 300ms），帮助看清发生了什么。
- 只有一个画面又没有分支的需求，可以按 takeover 文档的做法：用 2–3 个带步骤编号的静态画面讲先后顺序。

## 视觉与技术约束

- 页面 token（`--bg --paper --ink --muted --line …`）和产品 token（`--p-*`）分开定义，都同时写亮色和暗色两套：`@media (prefers-color-scheme: dark)` 下加 `:root:not([data-theme="light"])`，另外再写一份 `:root[data-theme="dark"]`。
- 内容最大宽度 1160px，左右留白 16px；小于 820px 时网格变成单列，演示窗口改为上下堆叠，宽表格和 SVG 用 `overflow-x:auto` 包起来。
- 中文正文，标识符、路径、命令保持原样。句子要短，讲清"是什么、为什么"，不写营销腔。

## 不要做

- 不要编造接口、字段或配置。找不到出处时写"待确认"，放进第 05 节。
- 不要为了做文档去改业务代码、跑 `pnpm fmt/lint/typecheck`，也不要启动会和用户实例抢端口的服务。
- 不要把页面写成大段文字，能用演示或图说明的就不用段落。
